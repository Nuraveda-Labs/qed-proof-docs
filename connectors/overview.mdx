title: Connectors
description: How QED Proof connects to a destination, what each connector reads, and which ones can verify a claim today.
---

A connector is a read-only connection to a destination: GitHub, GitLab, a Facebook Page, an Instagram account, a
Meta ad account, a Slack workspace, or an X account. Connecting one lets QED Proof read the facts a verifier
needs — it never lets QED Proof write, post, edit or delete anything there.

Not every connected destination can be checked yet. Two things are true at once for most connectors today:

- **You can connect it now**, read-only, and see what QED Proof would read.
- **Verification isn't built for it yet.** No claim against that destination can be decided until a verifier for it
  ships.

<Note>
GitHub, Slack and X have live verifiers today. GitLab, Facebook Pages, Instagram and Meta Ads can be connected, but
claims against them aren't checked yet. WhatsApp and Gmail aren't connectable at all — see
[coming soon](/connectors/coming-soon).
</Note>

|---|---|---|---|
| [GitHub](/connectors/github) | Code | Yes | Live — `github.commit.push`, `github.pr.open`, `github.checks.pass` |
| [GitLab](/connectors/gitlab) | Code | Yes (read-only) | Not built yet |
| [Facebook Pages](/connectors/meta) | Social | Yes (read-only) | Not built yet |
| [Instagram](/connectors/meta) | Social | Yes (read-only) | Not built yet |
| [Meta Ads](/connectors/meta) | Ads | Yes (read-only) | Not built yet |
| [Slack](/connectors/slack) | Messaging | Yes | Live — `slack.message.post` |
| [X](/connectors/x) | Social | Yes | Live — `x.post.publish` |
| [WhatsApp](/connectors/coming-soon) | Messaging | Soon | Not built yet |

One action needs no connector at all: [`http.url.status`](/connectors/http) checks a public URL directly.

## Planned: more ways to connect

<Note>
Planned, not built. This describes a proposed design, with no timeline to share.
</Note>

Today, every connector is QED Proof's own one-click OAuth app. A proposed design would add three more kinds of
connection: pasting an **API key** for a provider that doesn't do OAuth well for server-side reads, defining a
**custom API check** against your own systems (a base URL plus declarative assertions, so you can prove an outcome
in software QED Proof doesn't know about), and connecting through **your own OAuth app** for providers that gate
their app review, rather than waiting on QED Proof's. All three would keep the same rule every connector follows
today: evidence comes from reading the destination, never from trusting what an agent reports about itself.
